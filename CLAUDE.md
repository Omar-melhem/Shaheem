# SHAHM prototype — agent instructions

Source of truth for requirements: SHAHM-SRS-001 v1.0 (Product Owner). Labels there
(CONFIRMED / INHERITED / PROPOSED / OPEN / PROTOTYPE) matter: never implement an
OPEN decision as if approved — make it a labelled demo assumption with its O-xxx ID
(see `OpenDecision` and `SimTag` in `src/shared/components/ui/DemoLabels.tsx`).

## Rules
- React 18 + TypeScript + Vite + Tailwind. Arabic-first, RTL; use logical classes (`ms-`, `pe-`, `start-`, `end-`).
- Brand colours come from `tailwind.config.js` tokens (primary #8C2335, secondary #263D34, ink #242424, cream #F5F0E8, sand #C8A98A). Use the logo via `<Logo />`; do not alter the artwork. Sand-coloured **text** uses `text-sand-ink` (≥4.5:1); `sand-dark` is for borders/decoration only.
- Layering: `domain` (pure rules) ← `application` (use cases/store) ← `features` (UI). UI never owns pricing, dispatch, wallet or order-transition rules. `domain`/`application` import no React, zustand/react or browser APIs; the store is a vanilla `createApplicationStore(seed, repository)` over the `AppRepository` port. Concrete adapters (`infrastructure/browserState.ts` localStorage, `infrastructure/session.ts`) are wired only in the composition root `src/app/state.ts` / `src/app/session.ts`; features import `@/app/state`, `@/app/session` and `@/shared/hooks/application`, never `@/infrastructure` (except `placeSearch`).
- Use cases return `Result`; surface them with `reportResult()` toasts.
- Money is integer fils (`jodToFils`, `formatMoney`). No floats for money.
- Pricing: fixed fee per merchant + zone (Zone-Based Pricing Spec), read-only and locked on the order (`resolveZoneFee`, re-checked in `createOrder`). Never distance-based, and a pin never changes the fee.
- Request form (CR v1.4 §4, §6): first «طلب فوري» or «طلب مؤجل»; a delivery **location is required** (owner review 2026-11-21), satisfied by the area list or a map pin: the order always carries `areaId` (it sets the fee); a pin dropped before choosing an area selects the Merchant's area containing it (`detectAreaForPin`: exactly one bounded, covered and priced area, never a guess; otherwise `PIN_OUTSIDE_COVERAGE`). Empty → `LOCATION_REQUIRED`. The customer phone is optional (owner decision 2026-11-15) but, when given, must be 10 digits starting with 07 (`isValidOptionalPhone` + `CUSTOMER_PHONE_ERROR`, in the form on blur/submit and in `createOrder`; blank is stored as absent, never a placeholder number; views show «غير مضاف» and no call link); **there is no customer-name field anywhere** (Master Prompt §13: not in the form, payload, order type, seed, or any view). An optional «مجموع الطلب» (goods total, owner 2026-11-25) is stored in `mealValue` as integer fils (`domain/orderTotal.ts`: blank = absent, never 0.000; ≤ 99,999.999 JOD) and shown in the review and order details; it never feeds the fee, the commission or revenue. Address description was removed; older orders keep theirs. The flow lives in `features/merchant/request-captain/`: validate → review dialog → one `createOrder`; the success toast never implies a Captain accepted.
- Exact pin (`domain/destination.ts`): never auto-placed; optional once an area is chosen. Anywhere inside the area's boundary **including the boundary itself** is accepted (`polygonCovers`, like `ST_Covers`; owner 2026-11-25); outside → «الموقع خارج منطقة التوصيل المحددة». A pin on a border shared by several areas is `ambiguous` (`matchAreaForPin`), never guessed. An area without a boundary refuses a pin (`AREA_HAS_NO_BOUNDARY`) — never treat the whole city as valid. The 5/10 km dispatch radius plays no part. The seed rectangles are approximate demo geometry, not authoritative boundaries. A mismatch is surfaced, never reassigned. An area-only order has no `destination.position`: never store a centroid, 0,0 or a guessed address, and show `NO_EXACT_LOCATION` to Captain and Admin (`isAreaOnly`).
- Date/time fields: only the shared `DateTimeInput` (native picker, LTR value, Arabic `emptyHint`, icon at the inline end, 48px/16px; WebKit fixes in `.shahm-datetime` in `index.css`). Never a bare `<input type="date|time">` — iOS Safari shows an empty one as a blank box.
- Dropdowns: only the shared `Select` (custom ChevronDown at the inline end with a fixed inset, native arrow hidden; `className` sizes its wrapper). No one-off select styling.
- Toasts are one global `Toaster`, fixed top-start of the viewport (top-right in RTL).
- Place search is OpenStreetMap/Photon via `src/infrastructure/placeSearch.ts` (demo provider, O-018).
- GPS cadence (`domain/location.ts`, owner 2026-11-25): Available with no delivery → a report every 60 s; active delivery → 30 s; offline/suspended → none. Stale after 90 s (`IDLE_STALE_AFTER_SEC`) — the interval is not the freshness. The web only reads reports; `application/locationReports.ts` is the browser stand-in for the Captain app (never moves the position; a lost signal sends nothing). Never present stale, demo or last-known locations as live.
- Live map (`liveMapPresence`): pins only for Available Captains with a recent report and Captains on a delivery with live GPS; a delivering Captain with stale GPS is listed beside the map, not pinned; offline/suspended Captains are not shown. Delivering pins carry a parcel badge (not colour alone).
- Captain commission (CR v1.4 §3, owner 2026-11-25): a **percentage of the order's delivery-fee snapshot** (default 20%, `settings.commissionBp`), never of goods value and never flat; `commissionFils` (basis points, integer fils, round half up — rounding awaits approval). Demo ledger in `application/walletLedger.ts`: the rate and amount are locked on the order at acceptance (`lockCommission` = the hold), one `commission_debit` keyed `commission:{orderId}` is posted at delivery (`settleDeliveredCommission`); orders accepted before this have no snapshot and are never charged; a low balance never blocks delivery. «أرباح شهم» = realised debits only (`commissionRevenue`, Amman day/month); top-ups and holds are never revenue. Admin edits the rate in Settings with confirmation and an `adminAudit` entry; it applies to new acceptances only. Top-ups: ≤ 5.000 JOD per transaction (assumption), idempotent `recharge:{operationId}`, receipt confirmation, no free-text reason. localStorage is not a financial transaction — production needs `docs/wallet-commission-backend-contract.md`.
- Never invent support phone numbers, emails or WhatsApp links.
- Delivery completion is confirmed by the Captain only (no OTP/photo/signature).
- Keep presenter-only controls inside the demo tools drawer, clearly marked.
- Scheduled requests (CR v1.4 §6): `requestType: 'scheduled'` + `scheduledPickupAt` (Asia/Amman, `domain/time.ts`, must be future). They never enter public broadcast or the round loop, even after their time (`isAutoDispatchEligible`, checked in `createOrder`, `dispatchPublic` and `dispatchRounds`). Admin coordinates on WhatsApp (copyable message, no automation, no customer data) and assigns privately; a declined private offer returns to the manual queue.
- Dispatch (owner 2026-11-25): `DISPATCH_ROUNDS` in `domain/dispatch.ts` — 1) 3 nearest eligible within 5 km, 2) next 3 within 10 km, 3) all remaining within 10 km; 60 s each; haversine from the **Merchant pickup**; nobody is offered twice per cycle; a round with nobody new in range is skipped; then the Admin queue with `queueReason` (`roundsEndedReason`: none eligible / none within 10 km / all offered) — never a 4th automatic round, never cancelled/delivered by expiry. Round-2 size, rounds 2–3 duration and the «3 within 5 km» reading are proposals awaiting confirmation. Engine: `application/dispatchRounds.ts`.
- Phones (FU §1.3): exactly 10 digits via `domain/phone.ts` (`isValidPhone`, `normalizePhone`; the customer phone also needs the 07 prefix) and the shared `PhoneField`; store re-validates. Never apply it to prices, amounts, coordinates or IDs.
- Region catalogue (CR v1.4 §1): Governorate → City → Area → optional sections (`parentId`, one level; `domain/regions.ts`), managed by name with bulk import — **no map, polygon or boundary editing in the Admin areas module**. Names are unique among siblings only. Each area and section is its own destination with its own explicit price (no inheritance). Stopping an area stops its sections. Service areas belong to a Governorate (`domain/governorates.ts`). Delivery routes (origin → destination) are separate records and never change pricing; Admin can no longer create them («مسار توصيل جديد» removed, owner 2026-11-25) — saved ones are listed (card hidden when none) and deletable.
- Merchant coverage (CR v1.4 §2): `coverage` records which destinations a Merchant serves; **coverage is not a price**. Orderable = active + covered + priced (`resolveZoneFee`, `merchantZoneOptions`). «تحديد جميع المناطق» covers every active destination in the catalogue (not search results); areas added later are never auto-covered. Merchants see a read-only, printable list at `/merchant/areas`.
- Merchant location (owner 2026-11-25): City → Area from the catalogue (any area, priced or not) + a location chosen **only by tapping the map or picking a search result** (`LocationSearchField bounded={false}` → unbounded Photon search; shop name, area or address). Markers are never draggable (merchant pickup and customer destination alike). A merchant may be registered anywhere valid — never blocked by an area boundary, delivery zone or dispatch radius; (0,0) = not set (`PICKUP_REQUIRED`). The Area is never derived from the coordinate. Registration grants no delivery coverage (that is `coverage` + prices). `cityId`/`areaId` null = legacy text address, valid until Admin changes it.
- Price copy (CR v1.3 §4): `application/pricingCopy.ts`. Default fills missing prices only; overwrite needs separate confirmation; every copy is audited in `pricingAudit`. Order fee snapshots never change.
- No merchant contact-person field and no captain vehicle data anywhere (owner, Master Prompt §15/§18): merchants keep only the business phone; do not reintroduce either.
- Dashboards: every overview number comes from `application/dashboard.ts` (`operationalKpis`, `platformKpis`, `scheduledForToday`, `merchantOrderOverview`). Components only format. Admin overview = header quick actions, «أرباح شهم» (`RevenueCard`: today / this month / all, realised commission only), KPIs (incl. «الطلبات المؤجلة اليوم» = `scheduledForToday`: scheduled orders whose pickup is on today's Amman day, any status except cancelled), account totals, latest orders (no chart, no alerts panel, no broadcast banner, no captain availability — that lives on Captains and the live map). Distribution Center queues come from `application/dispatchQueues.ts` (scheduled → needs Admin → waiting stacked on the right, offers on the left; one list per order). Public broadcast is switched only from the header pill (and Settings) via `BroadcastConfirmDialog` → `setPublicBroadcast`. Merchant home: form, then active deliveries (a Captain is assigned — `merchantOrderOverview.active`), then «بانتظار كابتن» (`waiting`: open orders without a Captain), then the last 3 finished orders → `/merchant/orders` (full history). A finished order opens `MerchantOrderDetail` (read-only; history shows status changes only, never internal notes or which Captain declined).
- Captain trip history (CR v1.4 §7): completed trips by Amman calendar day of `deliveredAt` (today, yesterday, the day before), a view only.
- Login brand: title «شهم درايف» and the tagline «نوصلها بشهامة ونحفظها بأمانة» (deliberately without tashkeel) live only in `features/auth/components/LoginBrand.tsx`. Desktop lockup: logo `h-32 lg:h-40`, bold title, medium-weight tagline, tight `mt-4` + `mt-2` spacing. The visual is the original approved one: a very faint watermark (`LogoWatermark`, 2.5% — owner review 2026-11-21) + the white SHAHM car driving along the road (`backgrounds/ShahmDeliveryCar` + `shahm-delivery-car.css`, parked under reduced motion). Don't redesign it or replace the car with a framed photo.
- Login form (owner review 2026-11-21): username placeholder is just the demo username (no Arabic text in the `dir="ltr"` input), no ⓘ next to the subtitle, errors «اسم المستخدم مطلوب» / «كلمة المرور مطلوبة» (13px field errors everywhere), focus moves to the first invalid field, a failed sign-in clears and focuses the password, and the sign-in error has a reserved slot so nothing jumps. One presenter panel «أدوات وحسابات العرض» (`DemoAccountsPanel`, collapsed, controlled) holds the demo accounts and the demo tools.
- Demo tools (`DemoToolsButton`) are never a global floating button: Admin and Merchant put them in the top bar (`headerActions`), the login page in its demo panel, the Captain mock-up beside the phone frame.
- Focus is brand green (`secondary`: `focus-visible:ring-secondary-300`, inputs `focus:border-secondary-400`, global outline #4f7466); red is for errors only.
- Area named once: show destinations through `destinationParts` / `destinationText` (`domain/destination.ts`), never `destination.label` next to `areaName`. Dates via `formatDateTime`/`formatAmmanDateTime` keep «ص/م» glued; date, time and name cells are `whitespace-nowrap`. Prices always `formatMoney` (2 decimals; `formatMoneyExact` is for commission rates only).
- Merchant-facing status wording: pass `audience="merchant"` to `OrderStatusBadge` / `OrderHistoryList` (`orderStatusLabel`); a failed dispatch reads «بانتظار كابتن – فريق شهم يتابع الطلب». Admin keeps «انتهى التوزيع دون إسناد». Merchant support never mentions «لوحة الإدارة».
- Logo: `/brand/shahm-logo-transparent.png` has real transparency. Do not use `mix-blend-mode` or filters to hide a background.
- Admin cancel: existing policy only (`CANCELLABLE_STATUSES`, pre-acceptance, O-029) through `CancelOrderDialog`. No merchant-side cancel.

## Components
- Shared primitives live one-per-file in `src/shared/components/ui/` (imported via `@/shared/components/ui`); they never import features. Reuse `SearchField`, `PasswordField`, `PhoneField`, `InputIcon`, `InfoTooltip`, `SettingsSection`/`SettingsRow`, `Field` before writing new markup.
- Admin features with several parts have their own folder: `admin/dashboard`, `admin/dispatch`, `admin/live-map`, `admin/service-areas`, `admin/merchant-pricing`.
- In `DataTable` cells put `dir="ltr"` on an inner `<span>`, never on the `<td>` (it reverses the phone card layout).
- Table row actions: icons only via `IconAction` in `RowActions` (36px, 18px glyph; 40px on phones), same order on every row, no desktop «المزيد» menu. A disabled action passes `disabledReason` (it stays focusable and says why). Merchants and Captains use `DataTable legendTitle` → one ⓘ «شرح إجراءات الجدول» in the toolbar above the table (`TableActionsHelp`, with a `description` per action); the parent `Card` must not have `overflow-hidden`.
- Admin Orders filters: one applied state (`admin/orders/OrderFilters.tsx`). From `md` the selects are inline and apply at once; below `md` they live in the «تصفية» sheet as a draft (applies only on «تطبيق الفلاتر», closing discards), with a count badge and removable chips.
- Inputs with `dir="ltr"` inside the RTL page: pad with `rtl:`/`ltr:` variants (see `INPUT_ICON_PAD`), not `ps-`/`pe-`, which would follow the input's own direction.
- Feature-specific components stay in their feature folder; pages compose them. Don't extract trivial one-offs.
- Web shells: Admin and Merchant both use `shared/components/layout/AppShell` (persistent right-side sidebar from `lg`, accessible right-side drawer below it; content takes the remaining width). Merchant pages are child routes of `MerchantLayout` (`/merchant`, `orders`, `areas`, `settings`; «دعم شهم» opens the support dialog). Admin has **no** support page or nav item (owner 2026-11-25); the stored contacts and store actions remain for Merchant/Captain views. Navigation items live in the layout; authorisation stays in `RequireSession`.
- Settings only hold real, role-specific items. Admin: operation (broadcast setting, round policy and GPS cadence read-only), «إعدادات العمولة» (editable, confirmed, audited), account, «إعادة تعيين كلمة المرور» for Merchant/Captain accounts (demo: one-time temporary password from `generateTemporaryPassword`, never shows the current one, audited without the password; production contract in `docs/owner-requirements-2026-11-25.md`), sign-out. Merchant: store info (read-only), account, sign-out. Areas, merchants and wallets have their own pages.
- Web sign-out lives only in Settings (`features/auth/SignOutSection` → `useConfirmedSignOut` «تأكيد تسجيل الخروج» → existing `useSignOut`); no «خروج» in headers or sidebars. The Captain app keeps its own confirmed sign-out; sign-in via `useDemoSignIn` (role routing from the account, not the UI).
- Settings pages wire only controls backed by real store state; everything else is read-only (`SettingsRow readOnly`) — no Save buttons that do nothing.
- Status groups: every count or group heading uses `orderStatusGroup` / `countByGroup` / `ORDER_GROUP_LABEL` (`domain/orderStatus.ts`): pending dispatch, scheduled pending, offered, needs Admin (`dispatch_expired`), active, delivered, cancelled — one group per order, same label and count on the dashboard and distribution center. Raw per-status badges use `orderStatusLabel` (admin = `ORDER_STATUS_LABEL`). On the distribution center the right column (~65%) stacks «طلبات مؤجلة — تنسيق يدوي» → «بحاجة لتدخل الإدارة» → «بانتظار التوزيع», offers on the left (~35%); one column on mobile. Live-map legend starts collapsed; `IconAction` has a native `title` for hover.
- Captain eligibility has one source: `captainEligibility` / `eligibleCaptains` (`application/captainQueries.ts`) for rounds, the private-assign dialog, acceptance and lists. When rounds end, `roundsEndedReason`: «لا يوجد كابتن مؤهل متبقٍ» only if zero captains are eligible; otherwise «عُرض الطلب على كل الكباتن المؤهلين ولم يقبله أحد». Show stored reasons through `describeQueueReason` (live eligible count).
- «GPS متأخر» on the live map = stale GPS **or** an active delivery with no status change for `LATE_DELIVERY_AFTER_MIN` (demo threshold, not an approved SLA).
- Hardening (audit 2026-11-21): `vercel.json` sends nosniff, X-Frame-Options DENY, Referrer-Policy, Permissions-Policy and a **Report-Only** CSP (fonts.googleapis/gstatic, *.tile.openstreetmap.org, photon.komoot.io) — add any new external origin there. Saved state is upgraded (`migrateAppData`: new fields get defaults, records are kept) then shape-checked (`isAppDataShape`) and falls back to seed; `AppErrorBoundary` replaces a blank screen; the sim tick swallows save failures; place search has an 8 s timeout and drops bad coordinates. Password rule lives in `domain/account.ts`. Auth and data are client-side by design (prototype only) — never ship this auth to production.
- Seed orders are numbered in creation order (SH-10001 oldest). Changing seed data requires bumping `STORAGE_KEY` in `infrastructure/browserState.ts` (now `shahm-demo-v9`) or existing browsers keep old data.
- Business category (`MERCHANT_CATEGORIES`, OPEN-FE-07 proposed taxonomy) is classification only — never use it for pricing, dispatch or eligibility. `null` = legacy «غير مصنّف»; never default it.
- Merchants cannot edit their profile, category, pickup location or prices (Admin-owned).
- Project skills: `.claude/skills/shahm-login-design`, `shahm-auth-forms`, `shahm-auth-ux`, `shahm-rtl-arabic`, `shahm-design-system`.
- Logo: always `<Logo />` / `LogoWatermark` (transparent official PNG, no CSS cropping). Motion only via `motion-safe:animate-rise|fade`.

## Verify
`npm test` (Vitest) and `npm run build` (tsc incl. tests + vite build) must pass; `npm run coverage` enforces the floors in `vitest.config.ts` (raise, never lower).
- `tests/logic.test.ts`: the end-to-end store scenario; each `check()` is one named test (`tests/harness.ts`).
- `tests/unit/domain`, `tests/unit/application`, `tests/unit/infrastructure`: unit tests by layer. Store tests use a fresh isolated store per test (`tests/unit/application/storeHarness.ts`: `newStore()`, in-memory `AppRepository`), never the app singleton.
- `tests/unit/shared`, `tests/unit/features`: component tests with Testing Library; add `// @vitest-environment jsdom` as the first line. Default environment is Node.
- Builders in `tests/fixtures.ts`. Changing a rule → add or update the test in the layer that owns the rule.
